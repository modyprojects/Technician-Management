### Test categories
1. **Catalog grants:** checks built from the system catalog prove default deny: RLS on every exposed table, only the explicit grants per role, `private` not exposed, no direct INSERT, UPDATE or DELETE on profiles, technicians, permissions, role permissions or audit logs, and every SECURITY DEFINER function follows `docs/security.md` §5 (non-exposed schema, fixed `search_path = pg_catalog, pg_temp`; `015_pg_temp_shadowing` proves that a type shadowed in `pg_temp` never reaches a function body).
2. **Users without access:** anonymous, signed in without a profile, and deactivated users read and write nothing.
3. **Technician A vs Technician B, with the D36 exception:** A sees and changes only his own visits and related rows. With A's visit 2 open, A reads the closed visit 1 of the same call (summaries, approved transcriptions, media, parts, follow-up reason, next-visit notes) but not a future or concurrent visit of B, signatures or signer names, B's field times or original recordings. Access ends immediately after re-assignment, cancellation, closure, deactivation or role change; after re-assignment A no longer sees the current server version (only the status of what he submitted). With `calls` on and `card` off, no card content is visible, also not through review items or change history.
4. **Escalation, including account approvals (D33, D34):** a Manager cannot create, reactivate or change the role of a Customer Service account without Creator approval (while pending: no Auth user, the account stays inactive, the role is unchanged); rejection with a reason and cancellation; immediate deactivation with audit and Creator notification; a Manager cannot approve requests, set or reset passwords, change emails, touch Manager or Creator accounts or his own, grant `manager` or `creator`, or change the matrix; the last Creator is protected; direct UPDATE of a profile's role, active state or test marking and of a Technician's Outlook email fails for every role; Customer Service with `conflicts` cannot resolve a change to a server-closed or cancelled visit (D14, D44); `aal1` vs `aal2` once MFA is enforced (Step 2); a test user cannot manage a real account. Matrix metadata (D51): seeded values have the status `temporary`; only the Creator can change a value or mark it approved; a key added later is denied by default; a temporary value never grants a hard-restricted capability.
5. **Tampered ids:** server functions called with another Technician's visit, call or operation ids, another user's profile id, a visit id paired with a different call, or an operation under another user are rejected, with generic errors.
6. **Delete and truncate, including `service_role`:** append-only tables (for example audit logs and change history) reject UPDATE, DELETE and TRUNCATE for every role, including `service_role`; foreign keys restrict deletes. Owner-level database access is outside this boundary; the audit hash chain is verified instead (`docs/security.md` §8).
7. **Integrity, including D17 and D19:** customer number required (D17), and the D17-required template labels stay required whatever `settings` allows (D35); one product per normalized SKU (trimmed, upper-case, unique), an existing product name is never overwritten by ingestion, product edits only with `products` (D19, D33); composite foreign keys keep test marking consistent; deferred constraint triggers (for example "טופל" requires a signature) hold when closing as a Technician, as a Manager with `card` off and as `service_role`.
8. **Call status rules (D38):** cancelling the only visit gives "ממתינה לשיבוץ", never a cancelled call; out-of-order closures use the latest closed visit by visit number, not sync time; accepting a conflict and correcting an outcome recalculate the status; a new invitation on a resolved call reopens it, keeping history.
9. **Invitation updates (D39):** a rescheduled older invitation does not overwrite a newer contact field; an empty optional field means no change; ties follow receipt order; a different SKU or customer number, or a different customer name for the same customer number, goes to review; a closed visit is never changed.
10. **Timestamps (D45):** a late device report after a correction; a double tap; re-assignment from A to B (each Technician sees only the reports he made); a clock off by a year is flagged, never rejected; a correction that clears a flag; original reported times are never overwritten.
11. **Signature text (D43):** the approval text changes during offline work; a superseded version is accepted and marked; an unknown version or a wrong hash goes to review and is never replaced by the current text.
12. **Test data and census coverage (D47):** census zero on a database built from migrations only; a migration that inserts test rows fails CI; catalog coverage (every table marked or on the justified exemption list, every bucket covered); test marking is immutable; a real record never references a test record; `microsoft_graph` is rejected until its approved migration (fails closed).
13. **Concurrency:** concurrent changes to visits of the same call leave the correct call status (one function with a row lock, D38); concurrent edits merge automatically only when safe, otherwise both versions are kept and the rejected submission is stored (D44); a repeated operation id is applied once; a second closure from another device goes to review.

## Canary rows check (runtime, D47)
The static migration guard (`scripts/check-migrations.mjs`) reads the SQL text, so it cannot prove that a migration changes no data. The canary-rows check runs the migrations and compares data. The guard stays as the first line; both run in the `Database tests` workflow. Design, measured runtimes, results and the review round: `docs/review/db-canary/README.md`.
- **What it shows:** against the local throwaway database only, a migration that removes, changes, copies or derives data from rows that already exist (canary rows), in `public`, `private` or any other schema (Auth, Storage, Vault, large objects ...), or that writes data into the schema (a comment, a function body, a default, an extension member or a role built from rows), fails. It is a **tripwire for accidental or careless data writes, not proof against a migration written to evade it**: a migration can detect the harness (see Limits). Against deliberate evasion the guard and independent review remain the defence. Real data is never involved: the canary rows are fictional and test-marked (D47).
- **How it runs** (`scripts/db-canary.mjs`, Node standard library, Docker, the pinned Supabase CLI; the database only, `supabase db start`, with no other service of the project running, because Auth, Storage and Realtime write to the database on their own):
  - Every run starts from a fresh local project with zero migrations (`supabase db reset --local --no-seed` from a temporary folder with the same `config.toml` and an empty migrations folder); the check verifies that `public` and `private` hold no relations and the migration history is empty.
  - Reference runs A1 and A2: no canary rows; migrations 1..N in file-name order, each as one transaction as `postgres`; a snapshot before and after each.
  - Canary run B: base canary rows outside `public` and `private` (`tests/db-canary/000_base.sql`), then for each migration: apply it, compare with A1, insert its fixture (`tests/db-canary/<version>.sql`), check coverage.
  - A snapshot holds every row of every table, partitioned table and materialized view outside `pg_catalog`, `information_schema` and `pg_toast`, plus the large-object catalogs, with each table's column list. Each value is the text of its type's **output function** (never `to_jsonb` or a cast, which a migration can redefine for a type it owns), with the JSON category of built-in types kept (numbers bare, booleans `true`/`false`, the rest strings, `null`). It also holds every sequence's `last_value`, `is_called` and start value (read from the sequence itself); the schema (`pg_dump --schema-only --binary-upgrade`, run inside the database container: binary-upgrade mode also shows extension members and their comments and stored defaults of added columns; object ids, transaction ids and sequence states are replaced by placeholders); hashes of cluster-wide state (roles, memberships, role settings, parameter privileges, subscriptions) and of the database's own properties; a within-run hash of role passwords, replication slots and replication origins; the list of event triggers; and the base types not owned by a superuser.
  - The migration text is sent to `psql` base64-encoded and run with `\gexec` (with `-X -q -v ON_ERROR_STOP=1 --single-transaction`), so `psql` never interprets backslash commands in a migration or fixture. File names are passed only as data (argv arrays, never a shell string).
- **Rules** (fail closed; the message names the rule, the migration and the table):
  - **R1:** in `public` and `private`, no row of a table that existed before the migration is removed or changed (runs A1 and B; reference rows included). A new column may appear on existing rows only as null, so a column added with a non-null default, a backfill, a generated column, a dropped column, a renamed column (a rename can change what values mean, for example renaming another column to `is_test`) or a value-changing type change fails.
  - **R2:** rows a migration adds to an existing table are the same with and without canary rows; a sequence in `public` or `private` whose state (value or `is_called`) changes differently is also an R2 failure.
  - **R3:** a table or materialized view created by a migration holds the same rows with and without canary rows, and the schema after the migration is the same in both runs: tables and columns, the full binary-upgrade schema dump, cluster-wide state and the database's properties.
  - **R4:** outside `public` and `private`, a migration adds, changes and removes no row (Auth users, Storage buckets and objects, Vault secrets, cron jobs, queued HTTP requests, large objects ...), changes no sequence (`nextval`, `setval`, `RESTART`), and sets no role password and creates no replication slot or origin (compared within each run, because passwords carry random salts).
  - **R5:** volatile columns (for example `now()`, `gen_random_uuid()`) are the columns whose values differ between A1 and A2, found **per migration step** from the rows that step adds (and per snapshot point for the determinism check), so a column that is volatile in earlier reference rows never hides data in rows a later migration adds. Within a step, masks are refined per group of rows that agree on every other column, and a value that is equal in A1 and A2 must also appear in run B, so a deterministic row added next to a `now()` row cannot carry data. Masked columns are listed in the output; a masked value keeps its shape (every run of hexadecimal characters becomes one `0`), so a random UUID still matches another, but copied text does not. A fixture never consumes or sets a sequence.
  - **R6:** after each migration and its fixture, every table in `public` and `private` has a row and every column a non-null value somewhere, except reasoned entries in `tests/db-canary/coverage-exceptions.json` (three entries for `public.role_permissions` `approved_by`, `approved_at`, `updated_by`, added with PR 1.3's fixture; they narrow the check and need the owner's approval before PR #12 merges). The file is global: an entry applies to every step in which its table or column exists, and an entry that matches no step is stale and fails. A missing fixture fails with the file name to add.
  - **R7:** any SQL error (including a migration that fails only when canary rows exist), Docker or CLI failure, unparsable output, nondeterminism between A1 and A2 (rows or schema), another service of the project running, a migration that adds, changes or removes an **event trigger** (a login or DDL trigger runs code later, which the check cannot see; triggers of superuser-owned extensions such as `pg_tle` are not counted), a **base type not owned by a superuser** (`pg_tle`'s `create_base_type`: its output function could hide part of a value), or a fixture hygiene problem (a fixture only adds rows and never changes the schema; rows are test-marked; `example.test` addresses) fails the run. Zero migrations pass ("0 migration(s) checked"). The process exits 1 on every failure (2 on a usage error).
- **Fixtures:** `tests/db-canary/README.md` (one file per migration version where coverage needs one, written against the schema as of that migration and never edited after it is merged, fictional and test-marked, explicit ids, every column filled, including deactivated or closed variants). They live in `tests/db-canary/`, not `tests/db/canary/` as first planned: `supabase test db tests/db` runs every `.sql` file below `tests/db/`, subfolders included, as a pgTAP test (verified: a fixture there failed with "No plan found in TAP output").
- **Self-test:** `tests/db-canary-selftest/` holds 49 small self-contained cases (their own migrations and fixtures, `expect.json` with the expected outcome, rule and optionally a message fragment): passing schema changes, and failing cases for every rule, including one per bypass found in review round 1. The self-test runs every case and checks the rule that fired. For speed it resets once and clones that zero-migration database into a separate database per run (`CREATE DATABASE ... TEMPLATE`); when a run changed cluster-wide state it drops the roles, replication slots and origins the run added and falls back to a full reset if the fingerprint still differs. The check itself always uses full resets. In CI (D54) the check runs on every `Database tests` run, and the self-test runs only when the check's own files change (`scripts/db-canary.mjs`, `tests/db-canary/**`, `tests/db-canary-selftest/**`, `.github/workflows/db.yml`), and always on pushes to `main`; these files are on the protected list (`CLAUDE.md`).
- **Limits** (covered by the guard, review and pgTAP, not by this check):
  - **Environment detection:** a migration can tell the harness apart (the `psql` application name, the missing `supabase_migrations` history table, the fixed canary ids and `example.test` addresses, an otherwise empty database) and write only outside it. Applying migrations through the CLI would remove some signals but not the canary rows themselves, so the check stays a tripwire.
  - A write whose predicate excludes the canary rows (for example a real company domain, a specific id, or `is_test = false`: the canary rows are test-marked only, D54 (1)) is invisible to it.
  - Effects deferred to later calls (a function, trigger, rule, policy or default that changes data when the application uses it later) are not executed by a migration. Event triggers are refused (R7) because they fire without an application call.
  - A value of the same shape (hexadecimal or digits, for example a timestamp or UUID computed from data while the reference runs produce random ones) written into a column that is volatile in the same row group of the same step is hidden, as long as the row count and null-ness stay the same.
  - Anything in an excluded bookkeeping table (the list is empty today: no table changed on its own in the measurements).
  - The first migration has no earlier tables in `public` or `private`; R4 still covers Auth and Storage from the first migration.
  - Not compared: effects outside the database (network calls through extensions, files), planner statistics and object ids (OIDs).
  - The check's own files (`scripts/db-canary.mjs`, `tests/db-canary/`, `tests/db-canary-selftest/`) are protected files (D54, `CLAUDE.md`): a PR may still change them, but merging a change that weakens them needs the owner's approval, so review must name any such change.
  - Legitimate changes that rewrite existing rows or write outside `public` and `private` (a non-null default or a generated column, a column rename, a materialized view populated from existing rows instead of `WITH NO DATA`, a Storage bucket or a cron job created by a migration, an extension that ships reference rows such as `postgis`, an event trigger, a role password) fail by design and need an explicit, owner-approved way forward when they come.

## Offline end-to-end expectations (Step 4, D46)
- **Read-only cache:** data whose access was revoked (re-assignment, cancellation, closure, deactivation, role change) is purged at the next sync; retention follows D46 (final durations: open decision 12); other Technicians' recordings never appear in device storage.
- **Work queue:** pending work is never deleted, not at the end of the day, after cancellation or re-assignment, or after access is lost; it leaves the device only after the server confirms receipt and integrity.
- **Conflicts:** office cancellation vs offline closure: the cancellation stands, the closure and its media are kept for review, and if accepted the completion email is sent exactly once (D44, D09). A visit re-assigned or cancelled while offline: the cache is purged, the work is sent and kept for review.
- **Retries:** interrupted sync, backoff, manual retry ("נסה שוב", TE-24) and idempotent operation ids create no duplicates.
- **Warnings:** pending count on every screen and sync state per visit (TE-23, TE-24); warnings before sign-out, after a long time offline, on low storage (never deletion), when persistent storage is denied, and on iOS in a Safari tab instead of the installed app.
- **Deactivated account:** sync fails and pending work stays on the device with a clear warning (recovery path: open decision 25).
- **Environment mismatch:** the read-only cache is purged and queued operations are not sent; they are offered for export and review (D47).
- Unavoidable losses (device loss or damage, storage eviction, app removal, cleared browser data before sync) are documented in the user guides, not promised as recoverable.
