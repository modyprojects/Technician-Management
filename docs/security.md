# Security Blueprint and Verification Gates — HIGH PRIORITY

**Security assurance statement:** These controls reduce risk; no design document or automated scan can guarantee a system has zero vulnerabilities. Never import real customer data or launch until authentication, authorization, adversarial tests, backups and independent security review are complete. Real use starts only after Microsoft 365 is connected (D23).

## 1. Trust boundaries and threat model
Assets: customer identity/address/phones, technician schedules, photos, signatures, voice, transcripts, administrative privilege, email recipient addresses and API credentials. Attackers: unauthenticated web clients, compromised technician session, malicious calendar body, hostile uploads, compromised CI dependencies, mistaken admin, leaked secret and lost phone. Threats: IDOR/cross-technician leakage, role escalation, Storage URL leakage, API key exposure, SSRF, XSS, CSRF, replay, accidental production writes, and **test data leaking into real reports or real email**.

## 2. Key classification (Supabase 2026)
- **Public/publishable**: `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` is designed to be visible in the browser. Its safety depends on strict DB grants and Row Level Security. The project URL is not a secret.
- **Privileged/secret**: `SUPABASE_SECRET_KEY` / legacy `SUPABASE_SERVICE_ROLE_KEY` bypass RLS. SERVER ONLY. Never in client bundles, `NEXT_PUBLIC_*`, source code, browser requests, logs, tests/snapshots, screenshots, error responses, analytics, prompts, PRs, Actions artifacts or Preview HTML.
- **External provider secrets**: email API, future Microsoft secrets, webhook verification keys and transcription credentials are server-only and added only once approved. No secrets in the repository.
- Prefer the publishable/secret key scheme; legacy `anon`/`service_role` naming is deprecated.
- Never output environment variable **values**, keys or credential inventories in chat or tool output. Inspect variable **names** or provider secret-status indicators only. The owner enters values directly in Vercel/Supabase settings.

## 3. Secret lifecycle and cloud connections
- Least privilege for Claude Code connectors, service principals, GitHub Actions and Vercel Preview; no standing unrestricted production database access for automated development.
- Separate development and production Supabase projects and provider keys from go-live, once the owner approves a production project (D30; go-live gate in `docs/deployment.md`). Before go-live the owner explicitly approves either that separation (recommended) or a cleanup of the existing database (D47; comparison and pre-launch acceptance checklist in `docs/deployment.md`); nothing is created now. During the testing period Vercel Production uses the development project with fictitious data only (D31 known deviation). Preview never points at a production database.
- `.env*` ignored except placeholder-only `.env.example`. CI secret scanning and dependency scanning before merge.
- Free plans only (D30): GitHub push protection, secret scanning and branch protection are not available for this private repository on GitHub Free. Replacement (owner answer 2026-11-01): Gitleaks 8.30.1 (pinned, checksum-verified, `--redact`) runs on the full history in CI and locally before every push (`npm run scan:secrets`, same pinned release and checksum); `main` is protected by process only (no direct pushes or force-pushes; squash-merges only per D53: every mandatory check has passed on the exact approved merge candidate, and merging any change that weakens protections in `CLAUDE.md`, `docs/security.md`, `.github/workflows/**`, `vercel.json`, `proxy.ts`, `app/dev/_gate.ts`, `config/release.json`, the canary-rows check's own files (`scripts/db-canary.mjs`, `tests/db-canary/**`, `tests/db-canary-selftest/**`; D54) or the static migration guard (`scripts/check-migrations.mjs`; D55) needs the owner's approval). The owner enables Dependabot alerts (free). CI still catches a secret only after it was pushed, so any leak means revoke/rotate.
- If a secret leaks: stop deployment, revoke/rotate at source, invalidate sessions as needed, audit logs, repair exposure, report to the owner without echoing the value.
- Pin and review CI actions and dependencies.

## 3a. Supabase access and secret values (D53, 2026-11-03)
- **Only one project:** Technician-Management (ref `ooxozvvrljjkyfduuiks`). Never access, list, read, query, inspect or modify any other Supabase project or organization resource, through any tool, CLI, API, script or subagent.

- **Secret values:** never read, request, list, copy, print or expose credentials, tokens, API keys, passwords or environment-variable values.
  - Only variable **names** (and existing source references) are inspected.
  - If a value is needed, Claude Code tells the owner the variable name, and the owner configures the value himself in the provider's settings.
  - The owner is never asked to paste a secret.

## 4. Authentication and session
- Supabase Auth email/password; admin-controlled invitations; no public sign-up and no anonymous sign-ins (D50, §4a). Admin create/invite APIs run only server-side with the secret key, and only after the caller's authorization was checked in the database under the caller's own session (D34, §5).
- MFA for Creator/Manager before production; tested recovery and reset flows; time-limited reset links; no open redirects; brute-force protection; generic errors.
- Secure HttpOnly, SameSite cookies via supported Supabase SSR patterns; server-validated sessions; revocation. No provider tokens in localStorage or IndexedDB. Anti-CSRF or verified Origin on state-changing actions.

## 5. Authorization and row policy
- RLS on all exposed tables, explicit grants, private Storage; default deny. Every policy requires an active profile. Test technician A, technician B, customer service, manager, creator and anonymous.
- Roles come from server-trusted data (`profiles`), never from client-sent values or Auth `user_metadata` / `app_metadata`. No user has direct INSERT, UPDATE or DELETE on profiles, technicians, permissions, role permissions or audit logs; every change goes through a server function. Manager cannot assign Creator or Manager, or change his own account or privileges.
- **Permission matrix (D33, 2026-11-03; resolves open decision 1).** Editable in the Settings screen, as in the demo; **only the Creator changes it**. It covers the Manager and Customer Service roles; Technician and Creator capabilities are fixed. Keys: `cal`, `calls`, `card`, `cancel`, `dashGen`, `dashTech`, `dashProd`, `export`, `settings`, `usage` (from the demo) plus `products`, `conflicts` and `recordings`. Defaults follow the demo: Manager has every key except `settings` and `usage`; Customer Service has `cal`, `calls` and `card` only (Customer Service cannot cancel until d08 is decided; the usage screen is not built until d13 is decided). **These values are TEMPORARY (D51):** each carries the status `temporary` until the owner approves the final values on the Step 10 settings screen; temporary values never override hard restrictions; a key introduced later defaults to denied unless approved; the full enforcement, auditing and tests are built in Step 1, not deferred. Pre-pilot gate: the owner approves the final permission matrix.
  - **Data keys** (`calls`, `card`, `settings`, `products`, `conflicts`, `cancel`, `recordings`) are enforced on the data: RLS, grants and server functions.
  - **Screen keys** (`cal` vs `calls`, `dashGen`, `dashTech`, `dashProd`, `export`, `usage`) gate screens and server functions and never bypass database and server-side authorization. Every export is authorized on the server. Accepted limitation for v1: a user with `calls` can read the same rows through the API, so turning `export` off is not a control against data extraction.
  - Matrix changes go only through a Creator-only server function (the Creator check reads `profiles`, never the matrix), take effect immediately and are audited in the same transaction. The matrix holds rows for Manager and Customer Service only, and its key catalog is closed.
  - **Fixed capabilities, never matrix keys:** editing the matrix; Creator/Manager account administration; D14 audited corrections and any conflict resolution that changes a server-closed or cancelled visit (Manager and Creator only); simulator access (D24); security settings; technician field capabilities.
  - Operational settings (D35) follow `settings`; the D17-required template labels (request number, customer number) stay required whatever `settings` allows.
- **Account administration (D34, 2026-11-03; clarifies D05).** Only the Creator creates, modifies, activates, deactivates or manages Manager and Creator accounts. A Manager manages Customer Service and Technician accounts:
  - Manager-initiated Customer Service account creation, activation, reactivation and role changes take effect only after the Creator approves. While a request is pending nothing changes: for creation no Auth user exists until approval, reactivation keeps the account inactive, a role change keeps the current role. Requests are pending, approved, rejected or cancelled; a rejection stores a reason; every step is audited; no automatic expiry (D25).
  - A Manager can deactivate a Customer Service or Technician account immediately, without approval (for example an employee leaves or a phone is lost); it is audited and the Creator is notified in the app.
  - Technician account creation, activation and reactivation by a Manager take effect immediately. Routine permitted profile or operational updates (name, work phone, invitation alias, technician colour and device) need no repeated approval.
  - Managers cannot set or reset passwords for others and cannot change an account's email; only the Creator can (or self-service reset by email if an email provider is approved in Step 2).
  - Every change to a Technician's Outlook email notifies the Creator in the app (no approval).
  - Customer Service permissions do not have to be a subset of the Manager's. A Manager must never gain extra privileges by creating, modifying or using a Customer Service account; the approval workflow and the credential rules close that path.
  - Authorization for every account action is checked **in the database under the caller's own session before any Auth admin call**: first a database function running under the caller's session enforces these rules and writes the audit record; only then does the server call the Auth Admin API with the secret key. A profile is never inserted through `service_role`.
  - Nothing ever promotes a user to Creator automatically. The first Creator is set once in Step 2 by a protected one-time server function, run only with the owner's separate explicit approval; it fails if a Creator exists (D49).
- **Previous visits (D36, 2026-11-03).** A Technician with a current authorized assignment on a service call (one of his visits on that call is scheduled, en route or in progress, and his profile is active with the technician role) can view, for **earlier closed visits of the same call** (visit number lower than his open visit): summaries, approved transcriptions, photos, videos, parts, follow-up reason and next-visit notes, and other authorized attachments, even if another Technician did them. He never accesses original audio recordings from other Technicians' visits, signatures or signer names, other Technicians' field times, or future or concurrent visits of others. The Technician who created a recording may access his own recording only to review and correct its transcription, while his visit is not yet server-closed or the transcript awaits his approval, subject to retention rules (open decision 12). Access ends immediately on the server when the assignment ends (re-assignment, cancellation, closure), the account is deactivated or the role changes; the device purges read-only cached data at the next sync (§6).
- **Original recordings (D37, 2026-11-03).** The Creator always has access. Manager: on by default through `recordings`; Customer Service: off by default through the same key. Only the Creator changes the matrix. **Every access to an original recording is audited.** Recordings are never exported (D11) and never cached on other Technicians' devices.
- **Enforcement of D36 and D37** is in the database (RLS and a media-read authorization function) and in private-storage authorization, not only in the UI: no direct client Storage access; the server issues short-lived signed links only after a database authorization check under the user's session (§6). Names and labels shown for a previous visit come from narrow functions limited by the same visit-read check, not by opening the underlying tables.
- Representative contact (D40): Technicians see only the responsible representative's name and authorized work phone number, through a narrow server function limited to their own visits.
- Every server action, API, export, signed-link generator, admin route and simulator endpoint checks session + role + resource membership at the time of the operation.
- Avoid the secret key for ordinary CRUD; isolate privileged operations in narrow server functions. SQL functions use safe ownership and `search_path`:
  - **SECURITY DEFINER helpers are allowed only when they enforce authorization**: they return a boolean or the caller's own ids (for example `has_permission()` or `my_technician_id()`), set the fixed `search_path = pg_catalog, pg_temp` (with `pg_temp` last; an empty `search_path` is not enough, because PostgreSQL then searches the session's temporary schema first for type and relation names, where any API role can create a domain whose code would run as the function's owner: PR 1.3 final review SEC-1), name every other object schema-qualified, use no dynamic SQL, and live in the non-exposed `private` schema.
  - Admin RPC bodies live in `private`; `public` exposes only thin SECURITY INVOKER wrappers, so every call runs under the caller's session first.
  - Deferred constraint-trigger functions that check integrity rules across tables (for example "טופל" requires a signature) may run as SECURITY DEFINER owned by a dedicated non-login role, under the same `search_path` and no-dynamic-SQL rules, so the rule is checked the same way for every caller. They cannot be called directly.
  - No view or definer function bypasses authorization (`docs/database-schema.md`).
- Product editing (D19) restricted to roles with `products` (D33) through a server function; ingestion never overwrites an existing product name.

## 6. Media, device cache and offline
- Private media buckets with **no direct client Storage policies**; original recordings in their own private bucket. The server issues a signed link for one path only after a database authorization check under the user's session (D36; planned media read and upload authorization functions, Step 4). Read links are short-lived (planned: up to 5 minutes) and upload links expire (planned: up to 2 hours); authorization is checked again when an upload completes. Validate file signature, MIME, extension, dimensions/duration, size and hash on the server; random filenames; links never logged or exported. Every original-recording link is audited (D37).
- Quarantined media (Step 4) is readable only by active office users with both `card` and `conflicts` and by the Creator; the Technician sees only its status. It is never deleted automatically.
- **Two separate device stores (D46, 2026-11-03):**
  1. **Read-only cache** (own visits, minimal customer data, pickup list, previous-visit information): own open visit until closed, re-assigned or cancelled; own closed visit until the end of that day; previous-visit information until the end of the scheduled day or a revocation signal at sync, whichever is first; customer data like the visit it belongs to; **other Technicians' recordings are never cached**. Purged at sync when access ends. Final durations are decided with open decision 12 before the pilot.
  2. **Work queue** (reports, photos, videos, audio, signatures, time reports): kept until the server confirms receipt and integrity (matching hash). **Never deleted automatically** because the workday ended, an assignment was cancelled or re-assigned, or access was lost. Conflicting data and media are preserved for authorized review (D44); the device copy stays until the server confirms.
- Each store is bound to the user and to an environment identifier issued by the server; an operation is never sent under another user. On an environment mismatch the read-only cache is purged and queued operations are not sent; they are offered for export and review, so a device never sends test operations to another environment (D47).
- **Previous-visit cache and revocation (D36).** On the server, access ends immediately on re-assignment, cancellation, closure, deactivation or role change, and signed links already issued expire with their short lifetime. While offline the device cannot know; it shows cached previous-visit information only until the retention limit above. At the next sync everything no longer permitted is purged from the read-only cache; the Technician's own unsynced work is never deleted.
- Safe retries: automatic sync while online and the app is open, backoff, manual retry and idempotent operation ids. Clear warnings for pending data: a visible pending count and per-visit sync state (TE-23, TE-24); before sign-out; after a long time offline; on low device storage (a warning, never deletion); when persistent storage is denied; and on iOS when working in a Safari tab instead of the installed app (separate storage, so field work happens only in the installed app).
- A deactivated account cannot sync; its pending work stays on the device with a clear warning until a recovery path is decided in Step 4 (open decision 25).
- **Unavoidable risks (documented; no recovery promised for data that existed only on the device):** device loss, theft or damage, browser storage eviction (persistent storage is not a guarantee), app removal (on iOS, removing the home-screen app deletes its data) or cleared browser data before sync. IndexedDB is not a secure vault: whoever holds an unlocked device sees the cache. Mitigation: early sync, prominent warnings, minimum PII and the user guides. Define device lock, logout, lost-device process and the response to user revocation before real use.
- Never cache privileged roles, provider keys, refresh tokens or unrelated customer records in the service worker. Clear stale records when permissions change.
- Offline operations: unique IDs, visit version check, idempotent replay, atomic completion and outbox, no blind last-write-wins (D44), never delete unsynced media automatically. Test on real iOS and Android phones and tablets before pilot (D27, D28).

## 7. Inputs, webhooks, exports, email
- Zod + database constraints on all input; contextual escaping and CSP; never render calendar body as HTML. External text is data, never instructions.
- Future Graph webhook: validate subscription and clientState, scope to permitted calendars, replay handling, missed-event reconciliation. No live credentials now.
- XLSX/CSV formula injection: neutralize leading `=`, `+`, `-`, `@` and control characters. Export only authorized filtered data; no media or signed URLs.
- Email recipients resolved server-side; templates escape untrusted data; no customer PII in logs; unique outbox key; retries with backoff. Exactly-once delivery cannot be guaranteed after provider uncertainty.
- Rate-limit auth, admin, uploads, exports, event and simulator endpoints; request size and pagination caps.

## 8. Privacy, auditing, observability
- Collect only needed data. Audit role changes, corrections, cancellations, exports, product edits and secret-access operations by actor/target/action/time, without raw customer data. Also audited: permission-matrix changes (D33); account requests, decisions, cancellations and deactivations (D34); every access to an original recording (D37).
- **Audit immutability boundary.** Audit records are append-only and written by server functions in the same transaction as the change. No role, including `service_role`, can update, delete or truncate them (TRUNCATE revoked plus a statement-level trigger). This protects the audit **against the app, the secret key and `service_role`, not against owner-level database access** (the SQL editor, migrations, and any Supabase organization member with SQL access). A hash chain (each record stores a hash of the previous record's hash and its own content) makes such changes evident; the Step 1 report includes its verification. Who has owner-level access is governed by the Supabase organization, a company/department account (D50); that is a planning assumption, not a verification of its security settings.
- Hebrew user-facing errors; no stack traces, customer data, keys or session material in responses. Instrument auth failures, unexpected elevated operations, suspicious exports and sync failures without logging payloads.
- Retention, raw voice deletion, backups, storage region, consent and the final device cache durations (D46 sets the cache policy; open decision 12) are OPEN; no automatic purge until approved. The D46 purge of no-longer-permitted data from the device's read-only cache (§6) is approved; unsynced work is never purged.
- No scheduled background jobs in the first release (D25).

## 9. Outlook invitation simulator (D24) and test data (D47)
- Enabled **only** by an environment setting (`CALENDAR_SIMULATOR=1`): on in development and Preview. In Production only while `config/release.json` `testingPeriod` is true, as a second lock (D90, owner 2026-11-19: Production uses the test database until go-live, D87); any unrecognised environment is refused. Off in Production from go-live (go-live gate). No UI toggle. The database does not enforce the switch yet (OQ-13: `ingest_calendar_event` is callable by office sessions); closing that is in the post-M7 hardening migration (go-live gate).
- Access: Manager, Creator and Customer Service; never technicians; never anonymous. Enforced on the server and in RLS, not only by hiding the menu. No public simulator API.
- Inputs validated with the same Zod schemas as the ingestion service. Simulated event IDs are stable so replays are idempotent.
- Every record created through the simulator is marked as test data. Fictitious data only.
- In test environments (development, Preview) dashboards, reports and Excel exports include test data and are clearly labeled "נתוני בדיקה". In Production the same applies while `config/release.json` `testingPeriod` is true (D91, owner 2026-11-19: Production uses the test database until go-live, D87); from go-live (`testingPeriod` false) test-marked records are never shown, counted, reported or exported there. Simulated visits never send real email in any environment. Until go-live, Preview and Production share the development project (D31), so the test-data rule is the only separation there; from go-live, separate projects (if chosen under D47) make the production rule a second line of defense.
- Every visit displays its source ("🧪 זימון בדיקה" / "📅 נקלט אוטומטית מזימון Outlook").
- When the simulator is disabled, its endpoints return 404 and its UI is not rendered.
- **Test data (D47, 2026-11-03).** Every record created for development, automated tests, demonstrations or the simulator is reliably marked as test data in the database (`data_source` / `is_test` on every data table, including test users, media, related records and audit references), stays traceable to its origin (source reference and creator on root records, passed on to child records) and is visibly labelled in the app ("נתוני בדיקה" / "🧪 זימון בדיקה").
- `data_source` fails closed: until Microsoft 365 is connected (D23) the database accepts only `simulator` (all remote development and demonstration data, created through the simulator and the single ingestion path) and `automated_test` (local CI only); `microsoft_graph` is added later by an approved migration (Step 11). `is_test` is set on the server (from the source or the parent record) and is immutable; the client never sends it.
- Test data can never be confused with real data: database rules prevent real records from referencing test records (child tables carry a composite foreign key with the parent's `is_test`; for people and reference data a one-directional rule lets a test record reference a real one, never the reverse).
- Test users: marked by the server and immutable; Outlook email in the reserved `example.test` domain; a test user manages only test targets; no test Creator in the remote project.
- Storage: separate `test/` and `live/` prefixes in every bucket, including quarantine.
- Migrations never contain fictitious data: only schema and owner-approved real reference values (D48). CI fails if a migration inserts test rows, and a database built only from migrations must return a test-data census of zero. The census covers every table and bucket and lists its coverage; a CI check built from the catalog fails for any table that is neither marked nor on a justified exemption list.
- No automatic deletion of test data during development. Before real go-live: an explicitly approved cleanup or environment-separation plan and the pre-launch acceptance checklist in `docs/deployment.md`; the real app starts with no fictional content. No additional paid project or environment without explicit owner approval.

## 10. Mandatory security test matrix before every production-ready release
- Anonymous vs signed-in for every endpoint and storage path.
- Technician A cannot read or change technician B's visits, calls, media, signatures, downloads, notifications or local cache. **Exception (D36):** while A has a current authorized assignment on a call, A can read B's earlier closed visits of that call (visit number lower than A's open visit) as listed in §5. Tests prove that A never gets B's original recordings, signatures or signer names, field times, or future or concurrent visits; that access ends on re-assignment, cancellation, closure, deactivation or role change; and that the device purges the cached copy at the next sync.
- Manager cannot create Creator, escalate role, bypass approval or modify own privileges.
- Account-approval escalation (D34): a Manager's request to create, activate, reactivate or change the role of a Customer Service account has no effect while pending (no Auth user, the account stays inactive, the role is unchanged); rejection and cancellation are audited; a Manager cannot approve requests, set or reset passwords or change emails; a Manager's deactivation is immediate, audited and notifies the Creator; a Manager gains no privilege by creating, modifying or using a Customer Service account; direct updates of role, active state, test marking or a Technician's Outlook email fail for every role.
- Matrix (D33): only the Creator changes it; screen keys never grant data (with `calls` on and `card` off no card content is visible, also not through review items or change history); Customer Service with `conflicts` cannot resolve a change to a server-closed or cancelled visit.
- Recordings (D36, D37): a Technician never receives a link to another Technician's original recording and gets his own only while its transcription can still be corrected; Manager and Customer Service follow `recordings`; the Creator always has access; every link is audited; recordings never appear in exports or on other Technicians' devices.
- Test-data mixing (D47): a real record cannot reference a test record; test marking cannot be changed; an unapproved `data_source` value is rejected; a test user cannot manage a real account; migrations insert no test rows (census zero on a database built from migrations, catalog coverage complete).
- Archived/cancelled visits cannot be altered by old offline operations without conflict resolution.
- Double tap/retry/replay yields one closure and one outbox event.
- Simulator endpoints are unreachable when disabled, unreachable for technicians and anonymous users, test-environment dashboards and exports show the "נתוני בדיקה" label, production queries ignore test-marked records, and simulated visits never send real email.
- Preview and `/dev` cannot access production data. During the testing period (D31) Production holds fictitious data only and `/dev` may be served there behind Vercel Authentication; the go-live gate in `docs/deployment.md` removes it before real use.
- Browser JS, source maps, HTTP responses, browser storage, Git history, CI output, logs, screenshots and Vercel artifacts contain no privileged secrets.
- Revoked users, expired tokens, password resets, unauthorized exports, large/malicious uploads and server failure.
- Independent security review before real use; restore rehearsal for database and Storage backups.

- Vercel Authentication covers All Deployments (Preview and Production); the owner is the only team member.
- Never create shareable links, protection-bypass secrets, access exceptions or extra members; never use tools that create temporary share links; never pull OIDC tokens.
- These hold on **both Production domains** (`https://technician-management-mody-projects.vercel.app` and `https://technician-management.vercel.app`), and an anonymous request to each must be blocked (401 or redirect to the Vercel login, never 200).

- **Owner's checks (D53):** the owner's anonymous-access and dashboard checks are periodic; they are not required after every routine merge. An automated anonymous-access check is not implemented; the research is kept in `docs/research/d31-anonymous-access-check.md`.
- **On failure (D53):** a failed or inconclusive protection check stops further merges until the owner confirms; independent development and testing continue. Never disable deployment protection or bypass mandatory security checks.
- The `/dev` gate runs in `proxy.ts` before rendering; a closed gate returns 404 without showcase content.

## 11. Approval gates
Do not perform any remote Supabase write without the owner's approval of that operation (§3a, D53, D59); read-only operations follow §3a. Do not connect production Supabase or a live provider, send customer email, process real customer voice, import customer identities, run elevated SQL, loosen RLS, change permissions, enable the simulator in production, activate automatic deletion, or change cloud secret settings without explicit approval. The same applies to applying any migration, running the first-Creator function (D49), and cleaning test data or creating a production project (D47). Supabase Auth settings (§4a) are changed by the owner himself.
