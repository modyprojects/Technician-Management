## 4. בדיקות ההקשחה שנכשלות בצורה סגורה (fail-closed)

כל Migration מסתיים בבדיקה לקריאה בלבד. אם נשארה דליפה, היא זורקת שגיאה וכל ה-Migration מתבטל, כך שדבר לא מוחל:
- Migration 1, סעיף 15; Migration 2, סעיף 11; Migration 3, סעיף 12; Migration 4, סעיף 12 (העתק זהה של סעיף 12 של Migration 3).
- **מה נבדק בכל ארבעתם:** הרשאת CREATE על הסכמות; כל הרשאה ל-`PUBLIC`, `anon` או `service_role`; משהו מלבד SELECT על טבלה עבור `authenticated`; ברירות מחדל של הרשאות.
- **ובנוסף ב-Migrations 2–4:** טבלה בלי RLS; אובייקט שהבעלים שלו אינו `postgres`; מדיניות לתפקיד אחר מ-`authenticated`; פונקציה בלי `search_path` נעול; כל materialized view; וכל view (ב-Migrations 3–4 מותר רק view מסוג `security_invoker`, כמו `visit_time_current`).
- **בריצה הזו:** `supabase db reset` החיל את ארבעת ה-Migrations בהצלחה על מסד נקי, כלומר ארבע הבדיקות עברו. הקבצים `140`, `210` ו-`220` מוכיחים שהבדיקות אכן נכשלות כשמזריקים דליפה, ובדיקת ה-Node `hardening-assertion.test.mjs` (9) מוודאת שההעתקים בבדיקות זהים בייט לבייט לקוד שב-Migrations.
- **פערים ידועים** (`step1-pr14` סעיף 15.2, F-4): הרשאה עם GRANT OPTION, חברות בתפקידים, טריגר מושבת ועוד. Migrations 1–4 לא יוצרים אף אחד מהם, ורשימות ההרשאות המדויקות נבדקות ב-`010` וב-`130`.

- ברירות המחדל של `supabase_admin` בסכמה `public` מתירניות, ו-`postgres` לא יכול לשנות אותן. לכן אסור להתקין הרחבה בסכמה `public` (`step1-pr13` סעיף 10).
- ברירות המחדל של Storage מתירניות; שלב 4 חייב להקשיח אותן לפני שנוצר דלי כלשהו.
- גרסאות ה-Migrations בפרויקט האמיתי (`20261111125920`, `20261112093516`, `20261116094444`) שונות משמות הקבצים. זה מתועד ולא תוקן; תיקון הוא כתיבה בפרויקט ודורש אישור.

**שלב 2 (אימות וניהול משתמשים):**
- השרת חייב לשים את מזהה ההרשאה ב-`app_metadata.account_request_id` כשהוא יוצר משתמש Auth (`step1-pr13` סעיף 5).
- אימות דו-שלבי (`aal2`) ליוצר ולמנהל (החלטה פתוחה 19).
- התראה ליוצר באפליקציה, כולל על מייל Outlook של טכנאי חדש (`step1-pr13` N4).
- בדיקת קריאה של משתמש ה-Auth לפני יצירת היוצר הראשון (`step1-pr13` N5).
- Migration 5 (PR 1.8) לפני מסכי ניהול המשתמשים, לפי D60 (7)–(9).

**שלב 4 (עבודה בביקור ואופליין):**
- כותבי המכשיר: בדיקת שליחה חוזרת, ואז החלה או פריט לבדיקה, ואז רישום התוצאה, הכול בטרנזקציה אחת ב-READ COMMITTED; הכותב בודק בעלות על הביקור; ה-hash של התוכן מחושב בשרת (`step1-pr16` סעיף 5).
- כותב הסגירה, וטריגר `c50` על `visit_events` (`step1-pr15` S3).
- `previous_visits` יגדל (חלקים, מדיה, תמלולים) ויצטרך אותה סקירה; מדיניות `visit_media` תוסיף את `card` (`step1-pr15` N6).
- שאר מסלולי הפריטים לבדיקה (סגירה של ביקור שבוטל, אי-התאמה בטקסט האישור, התנגשות עריכה), והחלטה פתוחה 25.

**שלב 6 (קליטת זימונים וסימולטור):**
- כותב הקליטה: מוצר לפי מק"ט בלי לדרוס שם; קריאה בסטטוס פתוח עם הביקור הראשון והאירוע שלו בטרנזקציה אחת; סירוב לקשר זימון אמיתי לרשומת בדיקה; כל כותב הוא SECURITY DEFINER בבעלות `postgres` (`step1-pr14` F-7).
- מסלולי D39: העברה לטכנאי אחר, ביטול, שינוי כתובת, לקוח או מק"ט.
- ערך מזימון אמיתי שנכשל בכללי הטקסט יירשם כ"לא נקלט", ולעולם לא ייחתך (`step1-pr14` OQ-8).

**שלבים אחרים:** שלב 5: פונקציה צרה לטלפונים של המשרד, והערך העדכני אחרי תיקון בכרטיס הקריאה. שלב 8: נטרול ערכים שמתחילים ב-`+` או `-` בייצוא (הזרקת נוסחאות). שלב 9: טווחי ימים וחודשים בשעון ישראל. PR 1.8: החלפה נוספת של `tg_audit_target` תשנה שוב את טביעת האצבע של הביקורת.

supabase db reset --local --no-seed          # clean database again

git diff --check
