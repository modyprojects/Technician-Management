## 2. Design and security reasoning (`docs/security.md` §4)

**Request (`requestPasswordReset`).** The email is validated with the sign-in rule and lower-cased. If this environment cannot deliver (delivery `disabled`, no valid `SUPABASE_SECRET_KEY`, or no usable link origin) the answer is **delivery-off**, decided by the environment alone before any Auth call (it says nothing about any account). Otherwise the request itself does only the throttle and answers **sent**. Everything whose duration depends on whether the account exists runs **after the response** (`after()`): the Auth Admin `generateLink` (measurably slower for an existing account; independent review finding 1), any refusal (`user_not_found` …), the app's own link, the email and its log line. So the answer takes the same path, and about the same time, for every address (corrected after the review: the first version deferred only the email). The email goes to the account's own address as `generateLink` returns it (`data.user.email`), never the typed spelling (finding 4). Every well-formed request answers **sent**. One log line per request: an event name and an outcome code (`delivery_off`, `throttled`, `user_not_found`, `sent`, `mail_<code>` …), never the address, link or token.

**Why the app builds the link.** Supabase's own reset email would need its mailer (limited to the organization's members), its email template and its Site URL and redirect list, all remote settings. `generateLink` sends nothing and changes no setting; the app's link carries only the token's hash to the app's own `/login/reset`. Supabase's own `action_link` is never used.

**No open redirect, no Host-header injection.** The link's origin comes only from configuration (`APP_ORIGIN` or Vercel's system variables). A forged `Host` or `X-Forwarded-Host` header can never put another site into a real reset email. After a reset the browser goes to a fixed path (`/login?state=password-updated`); no `next` or redirect parameter exists in this flow.

**The link (time-limited, single use).** The token is verified only when the form is submitted (a server-action POST), never when the page is opened, so an email scanner or a prefetch cannot consume it. The Auth server keeps one recovery token per user (a new link replaces the old one), uses it once and expires it after the Auth "Email OTP expiration" (3600 seconds locally; see section 5 for the remote value). The page sends no referrer and loads nothing external; after the token is used the form drops it and removes it from the address bar.

**Setting the password (`completePasswordReset`).**
1. The password rules first: non-empty, at most 72 UTF-8 bytes, equal to the confirmation. A typo never uses up the link (also for a request that bypasses the browser's checks; tested).
2. With a token: `verifyOtp({ type: "recovery", token_hash })` under the browser's session cookies (the SSR client). A refused token gives the invalid-link state; a rate limit or service failure the service message.
3. The session must be a **recent reset session**: its verified JWT `amr` must hold an email-token verification no older than one hour. Pinned on the local stack: the reset link's session carries `amr: [{ method: "otp", timestamp }]`; a password sign-in carries `"password"` (`tests/auth/password-reset.spec.ts`). **Deviation from the design:** the design expected the method `recovery`; Supabase Auth names it `otp`. `otp` is also what an emailed sign-in link or code gives; each of those proves control of the mailbox exactly as the reset link does, and public sign-up is off (D50), so accepting it adds no new path. `recovery` is accepted too, in case an Auth version names it so. An ordinary signed-in session, a refreshed one (the `amr` keeps the original method and time) or an older reset session is refused: the invalid-link state, and the session itself is left alone.
4. `updateUser({ password })`. `weak_password` and `same_password` give a Hebrew message; the reset session stays, so the user retries without the (now used) link. Other failures give the service message. **The reset session is for the reset screen only** (review finding 2): `getSessionState` (`lib/auth/session.ts`) reads the session's verified claims (`getClaims()`) and treats a session whose `amr` holds `otp` or `recovery` but no `password` (or anything malformed) as **anonymous** in every app area: the guarded pages (`/office`, `/tech`, `/`) redirect to `/login`, and `/login` (also `?state=no-access`) and `/login/forgot` show their forms. A used link therefore never becomes a sign-in, also when the password change fails; the old password and the account's other sessions are untouched until a reset succeeds. A password sign-in keeps `password` in its `amr` across refreshes (pinned on the local stack), and the sign-in action does not use this rule, so ordinary sessions are unaffected.
5. Success: `signOut({ scope: "global" })` ends every session of the account (the earlier sign-ins on other devices too; tested), with the direct cookie removal of `lib/actions/auth.ts` as the fallback; then `/login?state=password-updated`.

**Generic errors, no enumeration.** The request screen shows the same heading and text for every address (tested against an unknown one); a refused, unknown or throttled request is indistinguishable to the user. A deactivated account (or one without a profile) can set a new password, but the sign-in rules are unchanged and still refuse it with the one credential message (tested).

**Brute-force protection.** Requests: the interim throttle (section 3). Token guesses: the Auth server's verification rate limit (30 per 5 minutes per IP by default) and the one-hour, single-use token. The token's hash is derived from the address and the one-time code (6 digits by default), exactly as for Supabase's own reset links and codes, so with the default length a distributed guesser has about a million candidates per address (review finding 3). The token can also be redeemed **directly at Supabase's `/verify` endpoint with the publishable key** (inherent to Supabase recovery tokens), bypassing anything the app adds; only the code's length and the Auth server's own limit cover that path. Every verification through the app comes from the app server's address, so the Auth limit then also caps the app as a whole. Hence three **mandatory go-live steps before `resend` is enabled anywhere** (section 3): "Email OTP length" 10, a durable per-address request cap, and an app-level cap on token submissions to `completePasswordReset`. Today no environment delivers an email, so no token reaches anyone.

**Secrets.** `SUPABASE_SECRET_KEY` stays server-only (never `NEXT_PUBLIC_`, never logged; the bundle scan passes). `EMAIL_PROVIDER_API_KEY` is read only by the dormant Resend adapter, which never puts it into a result or an error (tested). The mock delivery runs only where `VERCEL_ENV` is unset (local runs and CI) and only into the file `MAIL_MOCK_FILE`; everywhere else it is `disabled`. The in-memory list of the first version (live links in a server's memory) is gone (review finding 5).

**CSRF.** Next.js checks the Origin of every server-action POST against the Host (no `allowedOrigins`), as for sign-in (tested there with a replayed foreign-Origin POST). A request-reset POST replayed outside a browser with a forged `Host` and `X-Forwarded-Host` and a matching `Origin` passes that check by design, and its email still links to `APP_ORIGIN` (tested on the local stack, review finding 8).

**The token in the query string: an accepted low risk** (review finding 9). The link carries the token's hash as `?token_hash=…`, so it can appear in the browser's history and in the hosting platform's request logs (owner-only during the testing period). Accepted because the token is single-use (replaced by any newer request, used up by the first verification), expires after one hour, is verified only on a POST (never on opening the page), leaves the address bar after use, and the page sends no referrer (`no-referrer`) and loads nothing external. A fragment (`#…`) would hide it from the logs but needs client-side code to read it; not worth the complexity for this lifetime.

**MFA later (open decision 19).** When MFA is enforced for the Creator and the Manager, a reset session is `aal1`; Supabase Auth may then refuse the password change for an account with a verified factor, and the reset rules must be revisited with the MFA design (`docs/mfa-design.md`).

## 3. Interim throttle and the GO-LIVE BLOCKERS before `resend`

At most one reset email per address per minute (keyed by a SHA-256 of the lower-cased address; the address is never kept) and 20 per minute per server instance, in memory. A throttled request still answers **sent** and leaves the earlier link valid (a new `generateLink` would replace it). Vercel runs several instances and restarts them, so this is **no durable limit**. Today every environment is `disabled` or the local `mock`, and Preview and Production sit behind Vercel Authentication (D29, D31).

The per-instance cap counts every request, also for an address without an account (review finding 10): the throttle runs before the Auth call (finding 1), so it cannot know, and counting only real accounts would reveal them. So a stream of made-up addresses can use up an instance's 20 per minute and delay real requests on that instance. Accepted for the interim one; **how unknown addresses count belongs to the durable-throttle design** (for example a per-address cap kept apart from a global or per-client cap, or counting only messages actually sent, in a Send Email Hook).

**Mandatory go-live steps before `resend` is enabled in any environment** (each with the owner's approval; `docs/integrations.md` "Email"; D65):
1. A verified sending domain and the owner's approval of the provider (open decision 9).
2. Supabase Auth "Email OTP length" set to **10** (the owner's remote setting), confirmed by a read-only check; and "Email OTP expiration" at most 3600 seconds.
3. A **durable per-address request cap** (for example at most 5 reset emails per address per hour) in place of the interim per-instance throttle: a database-backed counter (a migration, with the owner's approval) or Supabase's Send Email Hook.
4. An **app-level cap on token submissions** to `completePasswordReset` (durable, per address or token and per client), so the app path adds no guessing capacity of its own. The direct Supabase `/verify` path stays covered only by step 2 and the Auth server's verification limit.

## 8. מה לבדוק (לבעלים)

- **מסך הכניסה:** הקישור "שכחתי סיסמה" ממורכז מתחת לטופס. שום דבר אחר במסך שאושר לא השתנה (לוגו, כרטיס, צבעים, גופנים, מרווחים).
- **אחרי איפוס:** ההודעה "הסיסמה עודכנה. אפשר להיכנס עם הסיסמה החדשה." מופיעה מעל הטופס, ברקע תכלת בהיר.
- **"איפוס סיסמה":** אותו עיצוב כמו מסך הכניסה (לוגו למעלה, כרטיס במרכז). לבדוק את הנוסח, את הכפתור "שליחת קישור" ואת "חזרה לכניסה".
- **"בדקו את תיבת המייל":** אותו מסך בדיוק לכל כתובת, גם לכתובת שאין לה חשבון (כך אי אפשר לברר אילו כתובות רשומות).
- **"שליחת מיילים עדיין אינה פעילה":** זה מה שיופיע היום ב-Preview, כי שליחת מיילים כבויה. אין שליחה אמיתית עד שתאשר ספק מיילים ודומיין מאומת.
- **"בחירת סיסמה חדשה":** שני שדות, לכל אחד כפתור עין משלו. הודעה כשהסיסמאות אינן תואמות. מסך "הקישור אינו תקף" עם "בקשת קישור חדש".
- **המייל:** תצוגה מקדימה ב-`/dev/email-preview/password-reset` (קישור פיקטיבי, שום דבר לא נשלח). לבדוק את הנוסח, הכותרת הכהה עם "MODY", הכפתור, שורת התוקף ("הקישור תקף לשעה ולשימוש אחד") והשורה התחתונה.
- **חשוב לדעת:** לפני הפעלת שליחה אמיתית דרך Resend צריך: דומיין שליחה מאומת; אורך קוד האימות של Supabase ‏(Email OTP length) של 10 ספרות (הגדרה שלך, עם בדיקת קריאה בלבד); הגבלת קצב קבועה לכל כתובת (למשל עד 5 בקשות בשעה) במקום הזמנית של היום; הגבלה באפליקציה על ניסיונות קוד; ואישור שלך. כרגע לא שונתה שום הגדרה מרוחקת.
- **אחרי תיקוני הסקירה הבלתי תלויה:** קישור איפוס משמש רק למסך "בחירת סיסמה חדשה". גם אם שמירת הסיסמה נכשלה (למשל סיסמה חלשה), הקישור לא מכניס לאפליקציה: כל מסך אחר מחזיר למסך הכניסה. המראה של כל המסכים לא השתנה.
