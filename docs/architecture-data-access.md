# Typed data-access layer

## Owner rule (2026-11-03)
- **Reads.** Screens read data only through a typed data-access layer: the ports in `features/*/data/ports.ts`. A fixture adapter implements them now; a Supabase adapter will implement the same ports later, so screens do not change.
- **No fixture data in components.** `components/**` receive DTO props whose types come from `features/*/data/types.ts`.
- **Actions.** Data actions (save, sign, upload, record, cancel and so on) go only through `useCommands()`. In the UI demo every action is simulated and marked "פעולה מדומה · לא נשמר" (D53).
- **Test data.** Every DTO record carries `isTest` (D47), so screens can show "נתוני בדיקה".

## Layout
| Path | Content |
|---|---|
| `features/data-access/common.ts` | Shared building blocks. Pure, no data or I/O, safe on server and client.<br>Types: `IsoDate`, `HourMinute`, `IsoTimestamp`, `TestMarker`, `Bounded<T>`, `Page<T>`, `PageRequest`, `CommandResult<T>`.<br>Limits: `MAX_PAGE_LIMIT` (100), `DEFAULT_PAGE_LIMIT` (40), `MAX_QUERY_LENGTH` (100).<br>Helpers: clamp and validation helpers, `boundedOf`, `pageOf`, `filterListValues` (an optional list filter: none or every value means no filter; a filter with no known value matches nothing, never every record), `ownValue` (an in-memory record by key, own keys only: "constructor" or "toString" read as not found) |

### `DataAccess` (read side)
Server Components and server functions call it.
- `calls`: `list(filter)` (paged, plus status counts), `get(req)` (the customer carries its card id), `customerHistory(req, page?)`, `backFromField({ asOf, technicianId?, page?, limit? })` ("חזרו מהשטח", OF-16: one row per call in "המשך טיפול" (D38: no open visit, latest closed visit "המשך טיפול"), that visit with reason, next-visit note, a summary excerpt of at most 140 characters, technician, customer with id, city, product, days waiting and cancelled later visits; oldest first; a next visit takes the call off the list, a cancelled one does not; `outlookConnected` is false until Microsoft 365 is connected (D23), so the "new Outlook invitation" action stays disabled with a hint, OF-08 pattern).
- `customers` (matrix key `calls`): `list({ q?, page?, limit? })` (name, customer number, phone with or without dashes, city; by `latestVisitDate`, the newest call's latest or next visit, newest first, as the calls list orders calls ("ביקור אחרון / הבא"); paged), `get(id)` (details from the latest invitation, the latest visit's address (D39), status counts, the calls (at most 40, newest first; more → the calls list searched by customer number) and the products (at most 20; returned products first) with `cameBack` and the returns, and `returnWindowDays`, the window the server used, which the card shows). A customer id is never the customer number. A product "came back" when the customer's next call for the same SKU opened at most `PRODUCT_RETURN_WINDOW_DAYS` (30, TEMPORARY, owner to confirm, pending d31) after the earlier call's latest closed visit.
- `products`: `list({ q?, page?, limit? })` (by SKU; SKU (normalized, PR-07), name, brand, supplier), `get(sku)` (input normalized; with the customer count and the latest 20 calls), `brands()`, `suppliers()` (Bounded, active and inactive). A row carries `brandId`, `supplierId`, `firstSeen` (the creating invitation: request, visit, date, source), `callCount` and `version` (D44).
- `intake`: `unparsedInvitations(page?)` ("זימונים שלא נקלטו", IN-03, IN-04): unresolved invitations, newest first, each with received time, source, subject, organizer, attendee (and the matched technician), the invitation's date and times, the request number and customer name when read, the problems (`missing`, `unknown-place`, `invalid` with the Settings label and the sanitized value; an unknown SKU is never a problem, IN-02) and `repMail` (pending d09, never shown as sent). Event-driven intake (D08); this layer only reads. The server gate of `intake` and of `calls.backFromField` waits for open decision #15 (d23): deny by default; the demo's fixed rule (`workQueueScreensOffered`) is not a grant.
- `visits`: `techDay(techId, date)`, `get(ref)`, `history(ref)`, `doneVisits(techId, date, page?)` ("הושלמו היום", paged), `doneVisit(techId, ref)` (the technician's own closed visit, read-only; null for an open visit or another technician's visit, D14), `corrections(ref)` (OF-10, D14: a server-closed visit's `original` and `current` correctable values, `correctable` fields (follow-up reason and next-visit note only for "המשך טיפול"), `version` and the corrections newest first, at most `VISIT_CORRECTIONS_LIMIT` (50); null when not found or not closed). For a technician, `history` returns only earlier closed visits of the same call (D36). Office reads (`calls`, `calendar`, `dashboards`, `visits.corrections`) return the current value (the latest correction); the fixture applies `_data/corrections.ts` to the seeded calls in `queries.ts`. **TEMPORARY (owner question, phase G):** the technician's reads (`visits.get`, `history`, `doneVisit`) return the values as the technician closed the visit, without office corrections and without any sign that a correction exists (the schema gives technicians no read on `visit_corrections`; deny by default). The alternative, the current values with a neutral "עודכן במשרד" mark, waits for the owner (`queries.ts` `CALLS_AS_CLOSED`).
- `review` ("פריטים לבדיקה"): `list({ status?, page?, limit? })` (newest first by receipt; `counts` per status regardless of the filter), `get(id)` (`ReviewItemDetail`: kind, source (an invitation with its SIM-14 source, or a technician device with operation id and device send time), the call and the visit, both versions per field (`base`, `current`, `incoming`, `conflict`, `choosable`; as stored when the item was created, D44), the D39 changes already applied with a notification, the offered `decisions`, `noteRequired` (true where the resolution changes a server-closed or cancelled visit, D14), `authority` ("closed-visit": Manager and Creator, a fixed capability; "conflicts": the matrix key), `completionEmailKey` (D44: accepting an offline closure of a cancelled visit sends the completion email exactly once), `version` and the resolution). An open invitation item whose visit has closed since offers "keep-current" only (D39: an invitation never changes a closed visit).
- `outbox` (developer tool only): `list({ page?, limit? })` (newest first), `get(id)` (`OutboxEmail`: subject, recipients with `fixed` and `pending` (D09 Manager and service mailbox fixed; d10 the Manager's scope and the handling rep), the EM-04 identifiers, the banner, the follow-up instruction, customer, product, technician, summary (written or approved transcript), recording length, parts, the signer with the approval text preserved at signing (D43), media counted and never attached (d11), the call-card link, the idempotency key (one logical notification per closure), `releaseDetail` (EM-05: "held" for a voice-only closure, pending d06) and delivery `blocked-test-data` (never sent, SIM-09); provider pending d12). The row is a snapshot at closure: later corrections do not change it.
- `sync` (the device's queue; production: the client-side offline module, Step 4): `device(techId)` (counts per queued state, `lastSyncAt`, visits with queue items first, at most `DEVICE_SYNC_VISITS_LIMIT` (30)), `visit(techId, ref)` (`VisitDeviceSync`: the TE-23 state from `visitSyncState`, the queued operations (at most 20) and `confirmedAt`; null when the device holds nothing about the visit). `DEVICE_SYNC_PROGRESSION` is what a close confirmation shows instead of any "email sent" claim.

The pre-D57 `managerAnalytics(period)` was removed when the screen switched to the tab methods. See "Metric definitions" below.
- `reference`: `technicians()`, `products(page?)`, `reasons()`, `places()`, `approvalText()`, `permissions(role)`. - `accounts` (paged): `list({ roles?, page?, limit? })` (by role, then name in Hebrew collation), `requests({ statuses?, page?, limit? })` (newest first). ### Metric definitions (manager dashboard, D57)
- **Registry** (`features/dashboards/data/metric-definitions.ts`): one entry per metric key (`today.*`, `service.*`, `top.*`, `trend.*`, `tech.*`, `prod.*`) with its tab, Hebrew label, unit, owner category, the records behind it, the group kind, the Hebrew definition, its source and the TEMPORARY interpretations it applies (T1–T8, T12, T13 under open #20; T9 withdrawn by D57 (5)). Owner categories (D57 (4)): approved and computed; "הגדרה ממתינה" (only `tech.planAdherence`); "לא זמין" (only `prod.topIssue`: no structured issue category). Screens read labels, states and definitions only from the registry; `detailOffered(key, tab)` and `detailRowsOffered(permissions)` (the dialog's rows need the data key `calls`, D33) are display helpers, never access control.
- **Formulas** (`features/dashboards/data/formulas.ts`): pure functions over `MetricCall` / `MetricVisit` (ISO instants, current values). Every function takes `scope` (`"test-env"` counts test-marked calls; `"production"` drops them before any computation, SIM-08) and dedupes calls by request number and visits by (call, visit number), first occurrence wins. Missing or impossible measurements are excluded and counted (`Metric.basis`, `Metric.excluded`), never 0; averages are weighted means rounded half up. Current call status follows D38; "% המשך טיפול" and first-visit resolution follow D57 (5) and never count visits.
- **Periods and time** (`periods.ts`, `time.ts`): Asia/Jerusalem dates via `Intl`; day / week (Sunday start) / month / year / custom periods with no future navigation (`MIN_OFFSET`, custom range ≤ 366 days ending today at the latest), the General chart's completed months, and `coverageStart`: the date of the earliest `opened_at` in the counted population (computed, never configured). A period entirely before it is "no data", never 0.
- **`now`** is passed by the trusted server page (the demo: `DEMO_NOW`, 21.10.2026 12:45), never taken from the URL. The demo adapter rejects a `now` without an explicit offset and a Technicians period that starts after its date.
- **Screen** (`app/dev/demo/office/[role]/analytics`): every view is URL state (`_state.ts`: tab, chart months, technician, period, offset, custom range, reports view, SKU page and sort, and the dialog's `detail`, `group`, `dpage`); `effectiveAnalyticsView` ignores whatever does not fit the role's offered tabs (no error, no data read). The page reads one tab method per request; a role without any dashboard tab reads no dashboard data. Display rules (G-04, D33; a production adapter enforces the same on the server and in RLS): the dialog's rows (`dashboardDetail`) and the reports view's rows (`technicianDetail`) need `calls`, its "תיעוד" and "חתימה" columns `card`, its 🎙 marker `recordings`; without `calls` neither method is called. The office frame is a segment layout, so `loading.tsx` (skeleton) and `error.tsx` (retry, no error details) render inside it.
- **Demo fixtures:** each call carries a fictional `openedAt` (two work days before its first visit) and `resolvedAt` (only for a D38-resolved call: the resolving visit's reported end as closed), added by a final pass in `seed.ts` that draws no random numbers. `customers.ts` `openedOn` (first visit date) is unchanged.

### `Commands` (write side)
Client components get it from `useCommands()`.
- `calls`: `cancelVisit`. OF-09 and SE-04 are PENDING (open decision d08), so no screen calls it yet: the call card shows a disabled placeholder. There is no reschedule or office-note command: neither is in the demo, the spec or `demo-deviations.md`, and scheduling stays in Outlook (OF-03).
- `visits`: `depart`, `arrive`, `setPickupCollected` (TE-03 "נאסף"), `saveSummary`, `addMedia`, `removeMedia`, `saveRecording`, `deleteRecording`, `saveParts`, `close`.
- `notifications`: `markRead(ids)`, `markAllRead()`, `setPreferences(prefs)` (TE-28, TE-29; the signed-in user's own notifications only).
- `settings`: `setPermission(role, key, value)` (Creator only; a `creator` role or a pending cell is rejected), `setTechnicianActive`, `addPlace`, `setPlaceActive`, `deletePlace` (unreferenced only), `addReason`, `setReasonActive`, `deleteReason` (user-added and never used only), `setFixedText` (a new version, D43), `addCallType`, `setCallTypeActive`, `setTechNotification`, `setTemplateLabelRequired` (a locked D17 label is rejected). The add commands return `CreatedSetting` (`{ id, isTest }` as stored).
- `products`: `update({ sku, expectedVersion, name?, brandId?, supplierId? })` (PR-06, matrix key `products`): never the SKU; `null` clears a brand or supplier; rejected for no change, an unknown product, a stale version, or an unknown or inactive option (`productEditError`, which runs `productUpdateError`, `productVersionError` and `productOptionError` in that order). Only the products page nests the simulated state that makes it pass (`productsState`); with nothing stored the edit fails ("המוצר לא נמצא", deny by default).
- `accounts`: `createAccount` (Creator; returns `{ account }`), `requestAccount` (Manager's Customer Service request, pending until the Creator decides; returns `{ request }`; the implementation checks the target's current role against stored data, `accountRequestTargetError`), `decideAccountRequest` (approve, or reject with a required reason; pending requests only), `cancelAccountRequest`, `deactivateAccount` (immediate, D34 b; never one's own account), `activateAccount`, `createTechnician` (immediate, D34 c; returns `{ account, technician }`, two ids). No password or email-change command (D34 e).
- `visits.correct({ visitRef, field, newValue, reason, expectedVersion })` (OF-10, D14; returns `{ correction }`): rejected for the signed approval text, the signer or the signature (D43), an empty reason, a stale version, a field the visit does not allow, no change or an inactive reason (`visitCorrectionError`). Only the call card nests the state that makes it pass (`correctionsState`, Manager and Creator).
- `review`: `resolve({ id, expectedVersion, decision, fields?, note? })` (`reviewResolutionError`: the input, the item, the caller (`reviewResolutionOffered`), open status, version, offered decision, an invitation's change to a visit that is closed now (D39: only "keep-current"; `source` and `targetVisitClosed` in the stored state), a choice for every conflicting field, the required note). Only the item page nests its state (`reviewState`).
- `sync`: `now()` (returns `{ attempted }`) and `retry({ opId })` (failed items only). The technician layout nests the device queue (`deviceQueueState`); elsewhere both fail.
- **Created records come from the command.** A screen shows the record a command returns (ids, `isTest`, times as stored) and never builds ids or test markers itself, so the Supabase adapter can replace the simulated one without changing a component.

## `CommandResult`
```ts
type CommandResult<T = void> =
  | { ok: true;  simulated: boolean; message?: string; data?: T }
  | { ok: false; simulated: boolean; error: string };
```
- **`simulated`** is `true` when nothing was saved, uploaded or sent. A screen never claims a real save, upload or email that did not happen (TE-23), and branches on it: a simulated result shows "בהדגמה … לא נשמר" and marks the changed row "לא נשמר · פעולה מדומה"; a stored result says what was done. Demo-only lines that do not depend on a result (for example "בהדגמה לא נשלחים מיילים") are passed by the demo page as a `note` prop, never written into a component.
- **`error`** is a short Hebrew message for the user, never a stack trace or server detail.

## How a Supabase adapter plugs in later (not built; needs approvals)
1. **Server-only reads.** A server-only module in `lib/` implements the same ports and runs per request under the caller's session. Authorization is enforced in the database: RLS, grants and server functions (`docs/security.md` §5). The secret key is never used for ordinary reads.
2. **Pages.** Pages call that implementation instead of `demoDataAccess`; screens and components stay unchanged.
3. **Commands.** Commands become server actions that validate input again on the server (`CLAUDE.md`: Zod for inputs) and return `CommandResult` with `simulated: false`. A `CommandsProvider` built on them replaces `SimulatedCommandsProvider`.
4. **Test data.** In production, dashboards never count test-marked records (SIM-08); in test environments they include them, with the label.
5. **Colours from the database.** Components put DTO colours such as `Technician.color` into inline styles. The production adapter accepts only an allowlisted colour token (for example `t-y`) and maps it to `var(--t-…)`; it never passes stored CSS through, so a stored value such as `url(…)` cannot make the browser fetch an outside address (TODO before the Supabase adapter).
6. **Account administration.** `AccountCommands` become server functions that check the caller's role in the database under the caller's own session before any Auth admin call (D34); the secret key never reaches a client. The matrix (`settings.setPermission`) is changed only through a Creator-only server function (D33), audited.
7. **Approvals.** Every remote Supabase operation and every migration needs the owner's approval (D52 rule 4, D53).

## ESLint enforcement (`eslint.config.mjs`; never weakened)
- **Shared code.** In `components/**`, `features/**` and `lib/**`, importing `@/app/*` or a relative `../…/app/*` is an error.
- **Fixtures outside `app/dev`.** Fixture modules (`_fixtures`, `demo/_data`, `demo/_components`) are blocked everywhere outside `app/dev`.
- **Demo screens.** In `app/dev/demo/**` outside `_data/**`, only five `_data` modules may be imported: `adapter`, `routes`, `roles`, `dates` and `params`. The error message cites the owner rule.
- **Known gap** (Phase A review): non-normalised paths and dynamic `import()` can evade these rules. No such case occurs in the code; normalising paths is an optional hardening.

## Bounded lists (`docs/security.md`: query bounds)
- **Paged lists (`Page<T>`):** default 40, at most 100 (`MAX_PAGE_LIMIT`). These are `calls.list`, `calls.customerHistory`, `calls.backFromField`, `customers.list`, `products.list`, `intake.unparsedInvitations`, `reference.products`, `notifications.list`, `visits.doneVisits`, the visit rows of `technicianDetail`, `accounts.list`, `accounts.requests`, `review.list` and `outbox.list`.
- **Phase G card lists (`Bounded<T>`):** a visit's corrections (`VISIT_CORRECTIONS_LIMIT`, 50), a device snapshot's visits (`DEVICE_SYNC_VISITS_LIMIT`, 30) and a visit's queued operations (`VISIT_OPERATIONS_LIMIT`, 20).
- **Card lists (`Bounded<T>`):** the customer card's calls (`CUSTOMER_CALLS_LIMIT`, 40) and products and returns (`CUSTOMER_PRODUCTS_LIMIT`, 20), a product's calls (`PRODUCT_CALLS_LIMIT`, 20), brands and suppliers (100).
- **Calendar lists (`Bounded<T>`):** `CALENDAR_LANE_LIMIT` (30) visits per technician per day, `CALENDAR_WEEK_DAY_LIMIT` (100) per office week column; month views carry counts only; at most one lane per technician (100).
- **Aggregate lists (`Bounded<T>`)** use fixed caps: `DASHBOARD_LIST_LIMIT` (20; the Products tab's supplier and brand bars always keep the "לא הוזן" row, appended after the cap when it falls beyond it), `TOP_SUPPLIERS_LIMIT` (3) and `TOP_SKUS_LIMIT` (5) on the General tab. `total` gives the full count, so a screen can say "ועוד X". The SKU table is a `Page<T>` of 20 rows and the details dialog a `Page<T>` of 50 (`DASHBOARD_DETAIL_PAGE_LIMIT`); the trend has at most 12 rows.
- **Settings lists** (technicians, reasons, places, call types, template labels) are capped at 100.
- **Other bounds:** search text is cut to 100 characters, and an analytics period (the Technicians tab, including a custom range) may cover at most 366 days. The Products & Suppliers tab is cumulative (all calls opened by `now`, spec §8.1); its output stays bounded (capped bars, a paged SKU table).
